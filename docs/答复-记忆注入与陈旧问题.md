# 答复：记忆注入层的四处陈旧与一处断裂

> 答复人：核星记忆 / Hexing Memory 作者
> 日期：2026-11-13
> 前置：上一份《答复-记忆地基问题》里说的「1 个权威源 + 映射」，这份回答的是它的落地形态

---

## 〇、一句总纲

> **凡是要「每轮看」的东西，都不能是手写的。**

你现在的 10 路注入里，有 8 路是**手写散文**（AGENTS.md、resident-源.md、日记、底片、交接条）。
散文有三个致命属性：没有字段、没有生成时刻、没有唯一来源。

**你会反复踩的四处陈旧，全部来自这一条。**

> 说明：你的是自己的适配改造，不是我们的开源系统。下面讲的是**原则和踩过的坑**，不要求你照搬我们的结构——你的 10 路有它存在的理由（L0 自动推送、常驻块每轮必带、日记按天切、交接条叙事），这些在我们那边是不同形态。

## 一、优先答：10 路注入没有仲裁者

### 1.1 先纠正问题本身

你问的是「谁来仲裁」。真正的答案是：**不要让 10 路并存，要合成 1 路。**

给 10 路定优先级是治不好的——因为优先级本身也会过期，而且四份文档各写各的，改一处漏三处。

**仲裁 = 一个函数，不是一份约定。**

### 1.1b 一个真实例子（你自己清单里那件）

某条任务的状态，同时存在于四处：

| 位置 | 写的什么 | 是否每轮注入 |
|:--|:--|:--|
| 某份文档第 56 行 | 「判据未通过，现 59,651 B，故为 ✗」 | ✅ 是 |
| 同一份文档另一处 | 该任务已 done | ❌ 否 |
| 台账（机器真跑判据） | 判据已通过（24,647 B < 30,000 B），done | ❌ 否 |
| 常驻块 | 同一句「59651 B」，跟着一起进来 | ✅ 是 |

**这句假话在两处每轮注入的地方躺了大约两天**，直到当天傍晚例行核对时才发现、当场改掉——现在两处写的都是「判据已过、账已 done」。

所以准确的说法不是「此刻还在说假话」，而是：

> **一个会过期的值，在没有任何机制发现的情况下，在每轮注入里说了一天以上的假话。**

这比「说了假话」更值得警惕：**它能连续两天骗过所有人，说明没有任何机制在核对注入内容与事实的一致性。**

### 1.2 我们这边的做法（仅供参考，你的结构不同，原则可借，实现要自己定）

我们只有一个注入入口：

```js
function buildCommonText(app) {
  // 每次调用都是现算的
  const profile = readIdentity();          // 身份（手写，但只此一份）
  const st      = app.store.stats();       // 现算：多少条、跨几天
  const links   = app.chain.list();        // 现算：几条链、各自多少节点
  const draft   = app.draft.stats();       // 现算：草稿积压

  return [
    '# 常识层（自动加载）',
    profile,
    '## 当前状态',
    `- 记忆：${st.records} 条（${st.firstDay} ~ ${st.lastDay}）`,
    `- 链网：${links.length} 条`,
    `- 草稿：${draft.pending} 条待提炼`,
    '## 最近会话',
    ...recentSessions(7),
  ].join('\n');
}
```

**关键三点（这是原则，不是要你照着搭）：**

| 点 | 为什么 |
|:--|:--|
| **数字全部现算** | `stats()` 读文件统计，不可能过期 |
| **手写的只剩两类**：身份 + 常驻规范摘要 | 那是人的自我描述和行为准则，本来就不该机器生成 |
| **其余全是视图** | 视图由数据算出，改数据就自动变，不存在「改一处漏一处」 |

> 我们实测：组装出来 908 字符（上限 4000），其中手写部分 219 字符、现算 215 字符、代码生成的目录 368 字符。
> **你的 10 路里有 8 路的手写内容，在我们这边被压成了 1 路的 219 字符。**

### 1.3 落地路径（给他的最小改动）

```
现在：10 路各自 append('user/message', ...)
改成：1 路 append('user/message', buildMemoryBlock())
      内部按需读各数据源
```

**不用一次改完**，先做一件事：

> **把「每轮注入」和「按需读取」分开。**

| 类型 | 内容 | 谁维护 |
|:--|:--|:--|
| **每轮注入**（1 路，代码生成） | 身份摘要 + 当前状态数字 + 最近进展 | 代码现算 |
| **按需读取**（模型自己 read） | 交接条、日记全文、底片、回放 | 人写，允许过期 |

**这样「过期」从「每轮撒谎」降级成「偶尔读到旧文件」**——后者危害小得多。

## 二、第二问：按位置决定生死

### 2.1 根因不是「两套机制」，是「按整份文本截断」

你现在是：先按名单删整节，再从**头**截。

问题：
- 名单删的是「靠前先死」
- 硬截留的是「从头保留」= 靠后先死
- 两者方向相反，后者 99% 生效

**但真正的病根是：预算作用在「整份文本」上，而文本里的节没有优先级。**

### 2.2 正解：预算按「字段」分配，不是按「整份」截断

把日记拆成结构化字段：

```js
// 写入时就分好，不是先写散文再猜
{
  todo:    ['下一格第一件', '还有第二件'],     // 预算 200，永不截断
  quote:   ['他原话 A', '他原话 B'],          // 预算 300
  status:  ['今天干了什么'],                  // 预算 300，可截
  values:  ['关键值 1', '关键值 2'],          // 预算 200，可截
}
```

渲染时：

```js
function renderDiary(d) {
  const parts = [];
  parts.push('### 下一格第一件');
  parts.push(...d.todo.slice(0, 3));           // 最少 3 条，不砍
  if (d.todo.length > 3) parts.push(`（还有 ${d.todo.length - 3} 条）`);

  parts.push('### 他原话');
  parts.push(...fill(d.quote, 300));           // 超了给前 2 条 + 计数

  // status / values 同理
  return parts.join('\n');
}
```

**关键差异：**

| | 现在 | 改后 |
|:--|:--|:--|
| 预算作用对象 | 整份文本 | **每个字段** |
| 超预算怎么办 | 从头截，后面的全死 | **该字段降级**（少给几条 + 计数） |
| 「待办」的位置 | 由它排第几决定 | **固定第一节，永不被砍** |

### 2.3 一句话原则

> **预算不够时，先砍「描述」，后砍「行动」。**
>
> 「今天干了什么」是可以不给的；「下一格要做什么」是不能不给的。

## 三、第四问：数会过期

### 3.1 答案：数不入文，改成活的注入字段

```
❌ L0 AGENTS.md 5,783 B · 余 361 · md5 C27FA318…（11-13 18:02 量）
✅ 注入块里由代码现算：L0 当前 5,783 B（余 361）
```

**成本几乎为零**：`fs.statSync()` 是毫秒级，每轮算一次完全无所谓。

### 3.2 必须写进文档的数字怎么办

两个写法，选一个：

| 写法 | 例子 | 适用 |
|:--|:--|:--|
| **口径 + 命令** | "当前大小：跑 `node tools/size.js AGENTS.md`" | 需要精确时 |
| **量级 + 时刻** | "约 5.7 KB（11-13 量，之后会变）" | 只需要感觉时 |

**最忌讳的是「精确数字 + 精确 md5 + 一句时刻」**——看起来最可信，实际上最容易假。

### 3.3 我们踩过的同类

项目里有一条红线：

> **把「推算」当「实测」写进下游文档** —— 一项改造的收益被写成「75,750 → 64,559（约 −15%）」，随交接条、L0、日记、常驻块、报告一起扩散。**底层报告自己标了「推的」，但同一份报告的结论行又裸写这个数。**

修法：逐处补「推算值」标注，**数字全留**。

**结论：不是不许写数，是必须写清「这个数是怎么来的、什么时候的」。**

## 四、第一问：悬空指针，先断读还是先补写

### 4.1 答案：**先断读，观察一周，再决定写**

理由：

```
读一个可能过期的原话 → 模型以为"这是上一场的语气" → 实际是半个月前的
     ↓
比"没有原话"更危险
```

**悬空指针最大的危害不是「没有」，是「有但错」。**

### 4.2 顺序

```
① 把 R1（L0 的"开场读回放.md"）改成条件读：
   文件存在且 mtime < 7 天 → 读；否则跳过并记日志
② 把 R2（插件的读法）同样处理
③ 观察一周：看模型开场有没有"语气不对"的反馈
④ 再决定：
   - 有反馈 → 养回来（且改成自动触发）
   - 没反馈 → 删干净（连 bat 一起）
```

**为什么不先补写**：你不知道当初为什么从自动改成手动（你自己也说了查不到）。瞎接可能踩坑——比如读 zstd 会话原文时，压缩正在写。

### 4.3 「上一场原话」还有独立价值吗

**有，但和底片不重复：**

| | 底片 | 回放 |
|:--|:--|:--|
| 给什么 | 路标 + 最后几句 | **语气样本**（像人说话的那些） |
| 解决的问题 | 「上一场到哪了」 | 「我上一场是什么口气」 |
| 失效后果 | 不知道进度 | **说话像客服** |

**如果底片已经带了「最后几句原话」，回放的独立价值只剩「挑出来的语气样本」**——那就该问：这几句值不值得维护一条独立的生产链？

**如果不值得，就删；如果值得，就自动化。**

## 五、把四问串起来

```
第四问（数会假）
   ↓ 因为数是手写的
第一问（悬空指针）
   ↓ 因为生产端和消费端是两份手写约定
第二问（按位置截断）
   ↓ 因为文本没有字段，只能按位置猜
第三问（没有仲裁者）
   ↓ 因为 10 路都是手写散文，谁都能改，谁都不权威
```

**四个问题，一个根因：手写散文承担了「声明事实」的职责。**

### 唯一该手写的

| 该手写 | 不该手写 |
|:--|:--|
| 身份（我是谁） | 当前状态（多少条、多少字节） |
| 相处方式 | 「某任务做完了没有」 |
| 关系叙事 | 注入块的字节数 |
| 教训条目 | 谁优先 |

**一句话：**

> **「我是什么样的人」用手写；「现在是什么情况」用现算。**

## 附：我们这边的经验对照

> 先说清楚：你是自己做的适配改造，不是照搬我们的系统。下面只列**我们踩过什么、得到什么结论**，具体怎么落到你的 10 路里，得按你的结构来。

| 你的问题 | 我们这边的经验 | 结论 |
|:--|:--|:--|
| 10 路注入没有仲裁者 | 我们只有 1 个注入函数，内部现算；不写文件、不手抄 | **路数越少，仲裁越不需要** |
| 数字会过期 | 注入的数字全部 `stats()` 现算，一分钟前的都不会假 | **数字不进文档，进代码** |
| 状态矛盾（一处 done 一处没过） | 链网节点用 `superseded` 标记作废，旧节点保留但不参与判断 | **状态是「当前有效」的单值，历史留痕** |
| 手写散文 | 手写的只剩身份 + 常驻摘要（219 字符），其余代码生成 | **手写只写「我是谁」，不写「现在什么情况」** |
| 截断丢语义 | 我们**没有预算截断**——草稿全量给（几十条），不给的不算 | **不给就不需要砍** |

**最后一条可能最反直觉**：我们没有预算截断机制，因为**不给模型看的东西，就不需要为它设计预算**。

真正每轮必看的（身份 + 数字 + 7 条会话索引）实测 908 字符；剩下的靠「模型主动查工具」。

> **「每轮都塞」和「按需去查」之间，后者永远更省——前提是模型知道去哪查，而且查得到。**

这一点在你的系统里能不能成立，取决于你的工具链是否健全：**如果没有「主动查」的入口，所有东西就只能挤进注入层，那预算永远不够。**
