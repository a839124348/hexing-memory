# XVEC v1 向量文件格式

> 定稿：2026-11-05 · 用于 v0.2 开源记忆系统
> 参考实现：`src/xvec.js`（约 150 行，含自测）

---

## 一、为什么是固定长度

向量文件的失败模式只有两个来源：

1. **同一条记录被写了一半**
2. **两个文件（或两个数组）之间对不上**

变长编码（JSON、protobuf、变长 int8 + 分隔符）会引入第三个问题：**必须知道"下一条从哪开始"**。这个"从哪开始"要么存在文件里（多一份要对齐的数据），要么扫一遍（慢，而且扫错了不报错）。

固定长度把这三个问题一次消掉：

- 第 N 条记录的位置 = `64 + N × 524`，**算出来的，不用查**
- 一条记录一次 `write`，**不会只写一半**
- 条数 = `(文件大小 - 64) / 524`，**除不尽就是坏了**

## 二、字节布局

```
文件 = 64 字节头 + N 条记录（每条 524 字节）

┌─────────────────────────────────────────┐
│ 头部 64 B                                │
├─────────────────────────────────────────┤
│ 记录 0   524 B                           │
│ 记录 1   524 B                           │
│ ...                                      │
│ 记录 N-1 524 B                           │
└─────────────────────────────────────────┘
```

### 头部（64 字节）

| 偏移 | 长度 | 类型 | 内容 | 说明 |
|:--|:--|:--|:--|:--|
| 0 | 4 | ASCII | `XVEC` | 魔数，不对就不是本格式 |
| 4 | 2 | u16 LE | 版本 = 1 | 不认识的版本必须拒绝加载 |
| 6 | 2 | u16 LE | 已归一化 | 1 = 向量模长为 1，可直接点积当余弦 |
| 8 | 2 | u16 LE | 维度 | 如 512 |
| 10 | 2 | u16 LE | 保留 | 必须为 0 |
| 12 | 2 | u16 LE | 记录长度 | `维度 + 12`，如 524 |
| 14 | 2 | u16 LE | 保留 | 必须为 0 |
| 16 | 32 | bytes | 模型标识 | `sha256(模型名字符串)` 的前 32 字节 |
| 48 | 16 | bytes | 保留 | 预留扩展，必须全 0 |

> **模型标识为什么用字符串的 SHA 而不是版本号**：模型名是用户能看见、能复现的东西（如 `BAAI/bge-small-zh-v1.5`），而模型文件的哈希会随量化版本、转换工具变化。用名字的 SHA 足够区分"换没换模型"，又不会因为无关因素误报。

### 记录（524 字节）

| 偏移 | 长度 | 类型 | 内容 |
|:--|:--|:--|:--|
| 0 | 512 | int8 × 512 | 量化后的向量分量，范围 -127 ~ 127 |
| 512 | 4 | float32 LE | 该向量的 scale |
| 516 | 8 | uint64 LE | id（与原文记录一一对应） |

**量化公式**：

```
编码：scale = max(|v_d|) / 127        （max 为 0 时取 1，避免除零）
      q_d   = round(v_d / scale)       ，截断到 [-127, 127]

解码：v_d   = q_d × scale
```

## 三、必须实现的四条校验

打开文件时按顺序做，任何一条不过就**拒绝加载并明确报错**：

| # | 校验 | 失败时的错误信息 |
|:--|:--|:--|
| 1 | 魔数 = `XVEC` | `不是 XVEC 向量文件` |
| 2 | 版本 = 1 | `格式版本 X 不受支持（本程序支持 1），请用 rebuild-index 重建` |
| 3 | 模型标识匹配 | `向量是用 X 模型生成的，当前配置是 Y，请用 rebuild-index 重建` |
| 4 | `(大小 - 64) % 524 == 0` | `文件尾部有 N 字节残缺（可能是写入中断），已截尾到 M 条` |

**第 4 条是自愈而非拒绝**：截掉尾部残缺记录、保留前面完整的，然后**写一条日志**。理由是——前面几万条都是好的，因为最后一条没写完就拒绝整个文件，等于让用户丢掉全部记忆。

## 四、追加的正确写法

```js
const fd = fs.openSync(path, 'a');          // 追加模式
fs.writeSync(fd, recordBuffer);              // 一次写 524 字节
fs.closeSync(fd);
```

**必须一次 `writeSync` 写完 524 字节**，不要拆成"先写向量再写 scale"两次调用。虽然两个 `writeSync` 之间被中断的概率极低，但固定长度格式的价值就在于**结构上不可能半条记录**，拆开就自己把这个保证放弃了。

多进程同时追加是安全的（实测 16 进程 × 1000 条 = 16000 条，0 撕裂），因为：

- 追加模式下，内核保证每次 `write` 的内容连续落盘，不会和别的进程交错
- 524 字节远小于单次写入的原子粒度（PIPE_BUF 通常 4096）

> **注意**：这个保证只在**追加模式**下成立。如果是"读出来、改、整份写回"，必须走临时文件 + `fsync` + `os.replace`（见规划书 §四之二.4），否则会丢数据。

## 五、读的正确写法

```
1. 读 64 字节头，做四条校验
2. 一次性读入全部记录区（或分块，见下）
3. 反交错：把 524 字节一条拆成
     连续的 int8[count × dim]   ← 用于扫描
     连续的 float32[count]      ← scale
4. 扫描时：score = Σ (query_d × q8[i×dim+d] × scale[i])
```

**为什么必须反交错**：如果扫描时逐字节 `readInt8(offset)`，10 万条会慢 1.33 倍（59 ms vs 44 ms）。反交错一次性只要 56 ms / 8 万条，之后扫描与 float32 完全打平（44 ms vs 44 ms）。

**大文件怎么办**：超过 2 GB 时不要一次读入，按"1 万条一块"分块读 + 分块反交错，扫描时按块累加。块大小必须是记录长度的整数倍。

## 六、体积与性能（81,609 条实测）

| 指标 | 数值 |
|:--|:--|
| 文件大小 | 40.8 MB（float32 为 159.4 MB，25.6%） |
| 转换耗时 | 519 ms |
| 载入 + 反交错 | 76 ms |
| 扫描（10 万条） | 44 ms（与 float32 持平） |
| 平均量化误差 | 0.000654 |
| 最大量化误差 | 0.001583 |
| 检索 Top10 重合 | 99.2% |
| 检索 Top1 一致 | 100% |

**估算公式**：`文件大小 ≈ 条数 × 524 + 64`

| 条数 | 体积 |
|:--|:--|
| 8 万 | 40.8 MB |
| 100 万 | 500 MB |
| 200 万 | 1.0 GB |

## 七、明确不做

| 项 | 原因 |
|:--|:--|
| 变长编码 | 会引入"下一条从哪开始"的对齐问题，破坏固定长度带来的所有保证 |
| 就地跨版本转换 | 容易出现"半新半旧"的混合文件，一律从原文重建 |
| 双文件（q8 + scale 分开） | 两次写，中途失败会错位且**不报错**，是本文档要消灭的头号失败模式 |
| 全库共用一个 scale | 每向量最大分量在 0.236~0.407 间浮动，统一 scale 会按最大者定步长，Top10 重合从 99.2% 掉到 97.5%（固定 0.349 时掉到 95.0%） |

## 八、迁移路径

| 场景 | 做法 | 耗时 |
|:--|:--|:--|
| float32 → XVEC | 本地换算 | 519 ms / 8 万条 |
| XVEC → float32 | 本地反量化，误差 0.0007 | 114 ms / 8 万条 |
| 换模型 | **从原文重建**（XVEC 里没有原文） | 22 分钟 / 8 万条 |
| 换机器 | **只搬原文 JSONL**，向量重建 | 22 分钟，与平台无关 |

**核心原则：原文才是迁移单位，向量是派生数据。** 只发 `XVEC` 不发原文，等于把用户锁死在你的模型上——模型一旦停更，用户的数据就再也读不出语义了。
