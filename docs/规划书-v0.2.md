# 开源记忆系统 · 规划书 v0.2

> 定位：把我们踩出来的记忆系统，精简成**个人用户**可用的开源版。
> 不是星枢（太重），不是商业多租户平台——就是"和我一样的个人用户"。
> 核心资产：**格式契约** + **踩过的坑** + **提炼层（后勤总管）**。

---

## 一、一条数据链（v0.2 修正）

```
AI 对话发生
   │  分钟级触发（实时同步，不烧钱）
   ▼
草稿（临时索引：可关键词搜、可语义搜）
   │  闲时提炼（空闲 N 分钟 或 草稿≥M 条）
   ▼
正式记忆（量化入库：原文存档 + 向量库）
   │
   └─→ 同时更新记忆库的数据层（链网 / 项目进展 / 事件节点，可增长，不常驻）
```

**为什么分草稿和正式**：
- 实时：聊着聊着就能搜到刚才说的话（草稿兜住最近几分钟）
- 省钱：不做实时向量化（那是每分钟烧钱），闲时一次做完
- 安全：草稿独立，提炼失败不污染正式记忆

**三条铁律**：
1. 多源进草稿，单点写主库——多少平台、多少窗口都可以往草稿写，正式记忆只有提炼层一个写入口
2. 记忆不可删除——记忆是存证，简化版也守同一原则
3. 格式由项目方定死——使用者不可改，校验不过不许导入

> 写路径单一指的是"主库只有一个写入者"，不是"只有一个 AI 在说话"。用户同时开几个窗口、手机和电脑一起用，都只往草稿写，不直接碰主库。

## 二、三层职责（v0.2 修正）

### 常识层（启动常驻）

常识层只放**固定文本**——长度不随对话增长的东西。会增长的数据（链网正文、项目进展、事件节点）不在这一层，放在按需层，靠入口去查。

| 内容 | 是什么 | 谁维护 |
|:--|:--|:--|
| 身份人格 | 我是谁、用户是谁。| 用户手写 |
| 编写规范 | 一份文档，含写入格式、校验与红线、链网怎么建、链网在哪怎么查 | 项目方 + 用户 |
| 说明书 | 数据迁移步骤、操作流程、验收单 | 项目方 |

**编写规范只有一份，不分散。** 格式字段、校验 15 项、回流防护、链网建法与入口，全写在这一个文件里（`RULES.md`）。说明书里不再重复这些内容，需要时直接引用，避免改一处忘一处。

**按需层（不进常识层，只给入口）**：

| 内容 | 为什么不常驻 | 怎么取 |
|:--|:--|:--|
| 链网正文 | 随对话持续增长，没有上限 | 编写规范里写明链名与查询接口，AI 自己去取 |
| 项目进展 / 事件节点 | 同上 | 同上 |

**为什么这么分**：常驻的代价是每一轮对话都要付 token。固定文本（身份、规范、说明书）总量可控，放进去划算；派生数据会无限长，塞进常驻等于让它把上下文吃掉。开源用户没有链网、没有项目档案也能正常用——缺的是数据，不是规范。

**估算**：身份人格几十到上百字；编写规范与说明书合计应在 1 万字以内。**超过 1 万字就说明写跑偏了**，那是文档没精简，不是常识层不够大。

### 草稿层（临时，分钟级）

- 存放 "已发生但还没提炼" 的原始对话
- 建临时索引，可关键词搜 + 语义搜
- 提炼成功入库后删除；失败则保留重试
- **多写者安全**：多平台、多窗口同时写，靠写锁 + 临时文件 + 原子替换兜住
- **检索方式**：直接做语义检索，向量只放内存不落盘；关键词检索作兜底。实测单条 embed 9 ms、50 条 0.5 秒，草稿量级下开销可以忽略。这样草稿和正式记忆共用一套检索逻辑，只差存储位置，少一套代码

**草稿层不做内容判重（v0.2 实测结论）**：

- **只按身份去重**：判重键是 `source + session + turn`。同一身份重复提交（网络重试、双写）丢弃；换轮次说同样的话一律保留。
- **不按内容哈希丢弃**。实测 81,609 条真实数据，按本层窗口（满 30 条或空闲 3 分钟）切成 7,289 批，批内逐字重复 1,754 条占 2.15%；其中模板噪音 1,135 条，真实发言 619 条、占 0.76%。这 0.76% 全是真话——同一批里连发两遍的留言、追问同一句——删掉不可恢复，而省下的存储可以忽略。
- **分批只决定"何时提炼"，不决定"存什么"**：无论一批几条、是否已提炼，草稿层始终保留全部原文直到提炼成功。临时召回读的是原文集合，不是判重后的去重结果，所以召回完整度不受影响。
- **模板噪音按类型排除，不删原文**：`system_reminder`、`additional_data`、会话压缩摘要、`Interrupted by user` 这类注入在检索时用 `type` 过滤掉，原文照旧保留。
- **时间只有分钟精度**：同分钟内逐字重复无法区分"重试"和"真说了两遍"，这是不能按内容判重的第二个理由。
- 内容判重放在**导入层**（校验器第 2 项），那里才是成批重复的来源。

**触发参数（三条同时生效，谁先到算谁）**：

| 条件 | 值 | 说明 |
|:--|:--|:--|
| 空闲 | 3 分钟 | 聊天自然停顿通常 1~2 分钟，3 分钟足够判断这段结束 |
| 草稿条数 | ≥ 30 条 | 按日均 383 条、单次会话 50~150 条估算，一次会话能触发一次 |
| 进程退出 / 会话关闭 | 强制落库一次 | 最重要的一条。否则"聊完就关电脑"的用户永远不入库 |

> 为什么不是 10 分钟 / 50 条：实测日均 383 条、中位一天 139 条、最多 489 条。10 分钟空闲在正常聊天节奏里基本不会到，50 条一天可能触发 3~10 次，两头都不合适。

### 原始存档层（正式，常驻不加载）

- 原文 JSONL，一行一条
- 原文直接向量化进向量库（不压缩、不改写）
- 召回 = 元数据过滤 + 语义检索 + 前后 2~3 条上下文
- **向量必须带 id，禁止靠行号对齐**（见第三节末）

### 提炼层（后勤总管）

| 职责 | 说明 |
|:--|:--|
| 实时集中 | 分钟级把对话收进草稿 |
| 闲时量化 | 空闲 3 分钟或草稿 ≥30 条 → 向量化入库 |
| 更新常识 | 写入链网、项目进展、事件节点 |
| 回流防护 | 剔除召回复述、打 origin 标 |
| 失败重试 | 草稿不丢、游标不推进 |

## 三、写入格式（契约，使用者不可改）

```jsonl
{"t":"2026-11-05 03:20","s":"用户","c":"原话一个字不改","cid":"conv-20261105-a1","v":1,"src":"zcode","type":"human","origin":"human"}
```

| 字段 | 必填 | 规则 |
|:--|:--|:--|
| `t` | ✅ | `YYYY-MM-DD HH:MM`，本地时区，精确到分 |
| `s` | ✅ | 说话人原名 |
| `c` | ✅ | 原文，一个字不改 |
| `cid` | ✅ | 会话 ID |
| `v` | ✅ | 格式版本 = 1 |
| `src` | | 来源平台 |
| `type` | | `human` / `ai` / `system` / `tool` |
| `origin` | | `human` / `ai` / `recall_echo` / `import` |

**语义规则**：一条 = 一次发言；不合并；不改字；UTF-8 + LF；系统消息单标 `type`。

**向量库存储规则**：每条向量必须带自己的 `id`（或 `cid`+`t` 复合键），与原文记录一一对应。**不允许靠"第 N 行向量 = 第 N 条原文"对齐。** 我们的 `archive_meta` 81,584 条 / `archive_vectors.bin` 159.3 MB 就是行号对齐，10 月底出过一次事故：meta 写了、bin 没写完，悬空 1,033 条，全部错位。多占几十字节，省掉一整类事故。

## 四、校验器（坑 → 校验项，15 项）

校验不通过 = 不许导入。

| # | 坑 | 校验项 |
|:--|:--|:--|
| 1 | GBK 当 UTF-8（542 处乱码瞒 4 个月） | 扫 U+FFFD，有即拒 |
| 2 | 重复条目 | 内容哈希 + 近似判重，**仅导入层**；草稿层按身份去重，见第二节 |
| 3 | 召回污染回流 | origin 检测（见第五节） |
| 4 | 日期错位 | 时间格式严格 + 会话内单调 |
| 5 | 索引/原文对不上（10-26 事故） | 索引必须能定位原文 |
| 6 | 块边界粘连 | 结构自检（块头计数） |
| 7 | 伪块标题 | 只认白名单块头 |
| 8 | 哈希口径不一致（62.4% vs 95.3%） | 规范化 + 定长后再哈希 |
| 9 | 召回碎片化 | 返回必须带上下文 |
| 10 | embed 挂掉假装没数据 | 降级显式标记 |
| 11 | 游标失效全量重炼 | 游标持久化 + 幂等 |
| 12 | embed 半路失败丢条目 | 失败不推进游标 |
| 13 | 时区切片错误 | 禁 UTC 直接切片 |
| 14 | 空内容 | trim 非空 |
| 15 | 时间格式漂移 | 严格格式 |

**校验器不是建议，是闸门。** 任一项失败，导入直接拒绝，不是警告、不是"先导入再修"。

## 四之二、性能与并发红线（全部来自线上实测）

这一节不是"建议优化"，是**写实现时必须避开**的写法。每一条都是我们线上真实跑出来的故障或实测，不是理论推导。

| # | 红线 | 一句话 |
|:--|:--|:--|
| 1 | 禁止 `bytes += chunk` | O(n²) 复制，48 MB 能拖到 328 秒 |
| 2 | JOIN 必须验执行计划 | 优化器可能先全表扫，7091 ms vs 155 ms |
| 3 | 性能改动必须证明输出不变 | 不能证明输出不变的"优化"等于改需求 |
| 4 | 所有落盘必须原子 | 覆写/追加中途崩溃都会留下残档 |
| 5 | 存档只追加，不整份重写 | 出现整份重写 = id 没设计对 |
| 6 | 检索必须无锁并发 | accept 队列默认 5，超过就拒连 |
| 7 | 量化省空间不省时间 | 缺空间才上，别指望提速 |

### 1. 禁止用 `bytes += chunk` 拼接

**坑**：解压 DSH 会话包（21.3 MB 压缩 → 48.6 MB 原文），代码是：

```python
raw = b""
while True:
    chunk = reader.read(65536)
    if not chunk: break
    raw += chunk          # ← 这里
```

bytes 在 Python 里不可变，每加一次就把已有内容整份复制一遍。48.6 MB 拼了约 740 次，实际是 O(n²)。

**实测代价**：这段解压 **328.9 秒**，占掉单日归档 67 秒里的 63 秒。换成 `chunks.append(chunk)` + `b"".join(chunks)` 后 **0.2 秒**，**快 1486 倍**，输出逐字节相同。

**规则**：任何"循环里往 bytes / 字符串上累加"的写法，一律改成"收集到列表 + 最后一次 join"。这条同样适用于 JavaScript（`str += x` 在 V8 有 rope 优化，相对安全，但大循环仍然别赌）。

### 2. JOIN 必须验执行计划

**坑**：从 ZCode 的 SQLite 取当天消息：

```sql
SELECT m.id, m.time_created, m.data, p.data
FROM message m JOIN part p ON p.message_id = m.id
WHERE m.time_created >= ? AND m.time_created <= ?
ORDER BY m.time_created ASC
```

看起来完全正常。但 `EXPLAIN QUERY PLAN` 显示它 **`SCAN p`** —— 先全表扫 part 的 19.7 万行，再逐行回查 message。**7091 ms**。

改成 `CROSS JOIN` 强制以 message 为驱动表：

```sql
FROM message m CROSS JOIN part p
WHERE p.message_id = m.id
  AND m.time_created >= ? AND m.time_created <= ?
```

走 `message_session_time_created_id_idx` 再按 `part_message_sequence_idx` 取子行，**155 ms，快 45 倍**，670 行结果逐条比对完全一致。

**规则**：任何带 JOIN 的查询，上线前必须跑一次 `EXPLAIN QUERY PLAN`，确认没有意外的全表 `SCAN`。SQLite 的优化器不看你"想让它怎么跑"。

### 3. 性能改动必须证明"输出不变"

上面两处都是纯执行路径改动。验收方式不是"感觉快了"，是：

- 新旧两版对**同一天**各跑一次，输出写到不同临时目录
- 逐文件比对 SHA1
- 比对条目数、条目内容
- 记录耗时对比

我们的结果：3 个文件 SHA1 全同，条目 `IDENTICAL=True`，67.55s → 4.71s。

**不能证明输出不变的"优化"，不算优化，算改需求。**

### 4. 所有落盘必须原子

**坑**：合并档原来是 `open(path, "w")` 直接覆写，追加用的是 `open(path, "a")`。两种都不是原子的：

- **覆写写到一半崩溃**（断电 / 被杀 / 磁盘满）→ 留下半个文件，当天的对话残了
- **追加中途崩溃** → 留下没有换行的半行，下一轮 `json.loads` 解析失败，那行永久卡死
- **两个进程同时追加** → 内容互相穿插，两条消息粘成一条

**正确做法**（我们改完的版本）：

```python
tmp = path + "." + str(os.getpid()) + ".tmp"
with open(tmp, "w", encoding="utf-8") as f:
    for line in lines:
        f.write(line + "\n")
    f.flush()
    os.fsync(f.fileno())      # 关键：确保真的落盘，不只是进 OS 缓存
os.replace(tmp, path)          # 原子替换
```

**追加也要走这条路**：读旧内容 → 拼接 → 原子重写。代价是多读一遍文件，实测 3.4 MB 只要 4 ms，完全可以忽略。

**必须满足的三条**：

1. 临时文件和目标文件**同一个目录**（跨盘 `os.replace` 会退化成复制+删除，不原子）
2. 必须 `fsync` 之后再替换（否则断电时可能替换了个空文件）
3. 失败要清理临时文件，别留垃圾误导下一轮

**行尾不要擅自改**：星核既有 111 个合并档全是 CRLF。加 `newline="\n"` 会让每次写入都变成全量 diff。跟随现有格式，或者在契约里明确指定一种。

**验收方式**：故障注入——写入中途抛异常，检查原文件字节不变、无临时文件残留、异常正常上抛。这条必须做，光看代码看不出来。

### 5. 归档为什么会整份重写（v0.2 的设计选择）

开源版**不要**照抄星核这条老路。星核之所以整份重写，是三个历史条件叠加：

1. 六个平台（WorkBuddy / ZCode / DSH / 桌面助手 / AionClaw / CodeBuddy）各存各的，必须汇成一条时间线才能排序
2. 存档文件被当成"当天汇总快照"，用"读旧档→合并去重→排序→重写"来保证幂等
3. 消息落盘后没有稳定 id，只能靠整行字符串比对判断"是否已写"

v0.2 的解法是**从源头避开**：每条记录带 `id`（见第三节），存档只追加，索引只追加。这样"排序"变成写入前的事（拿 id 排序），"去重"变成按 id 判重，"重写"整个动作消失。

**这条是硬性的**：如果实现里出现"每天整份重写存档"，说明 id 没设计对。

### 6. 检索必须无锁并发，不依赖外部向量服务（v0.2 硬性要求）

**这条不是优化建议，是硬性要求。** 开源版从第一天就要按"多个请求同时打进来"设计，不能等到用户抱怨了再改。

**为什么**：个人用户看着只有一个人，实际并发一点不少——AI 一轮可能同时发好几个检索；后台在提炼、前台在对话；开了两个窗口就在并行；定时任务和手动查询撞在一起。只要检索路径上有锁、或者要排队等一个单线程服务，这些请求就会互相堵住，表现为"聊着聊着突然卡两秒"。

**三条硬性约束**：

1. **检索不写盘、不拿写锁**——读路径全程无锁，写锁只保护写入
2. **并发在引擎进程内完成**——不依赖外部向量服务替我们排队（详见下面的实测）
3. **并发不能改变结果**——同一条查询并发 N 次，返回必须逐字一致

**我们踩到的真坑（星核 3.0 实测）**：

引擎本身是好的，检索路径确实无锁。但向量微服务用的是 Python `HTTPServer`，**默认 `request_queue_size = 5`**（内核 accept 队列长度）。超过这个数的连接直接被拒，不是变慢，是 **`ECONNREFUSED` 直接报错**。

实测梯度（同一查询并发 N 次，看成功数）：

| 并发数 | 6 | 7 | 8 | 10 | 12 | 16 | 32 |
|:--|:--|:--|:--|:--|:--|:--|:--|
| 成功 | 6/6 | 6/7 | 6/8 | 6/10 | 6/12 | 6/16 | 6/32 |

整齐地卡在 6，一眼就能看出是队列长度，不是算力不够。而且错误藏在引擎里，前端只看到"语义检索失败"，很容易误判成模型挂了。

**修法**：把 `request_queue_size` 抬到 128，`daemon_threads = True`，**处理仍然单线程串行**（保留防内存泄漏的设计）。改完实测：

| 并发数 | 6 | 8 | 12 | 16 | 32 |
|:--|:--|:--|:--|:--|:--|
| 改前成功 | 6/6 | 6/8 | 6/12 | 6/16 | 6/32 |
| 改后成功 | 6/6 | 8/8 | 12/12 | 16/16 | 32/32 |

320 次请求压完，常驻内存 443 MB → 444 MB，没有涨。

**关键结论：队列长度 ≠ 线程数。** 抬高 accept 队列只是让连接先排队进来，不会多开线程，也不会破坏"单线程防泄漏"的原有取舍。这两件事经常被混为一谈，改错方向就会去写多线程，反而把内存问题请回来。

**并发收益实测（星核 692 条向量，10 条不同强查询）**：

| 方式 | 耗时（7 轮中位） |
|:--|:--|
| 单条查询 | 18 ms（均值 20 ms，范围 11~33 ms） |
| 串行 10 条 | 285 ms |
| 并发 10 条 | 96 ms |
| **加速比** | **3.0x** |
| 20 并发 | 248 ms |
| 40 并发 | 121 ms |

**冷层对照（archive_semantic，8 万条原文向量）**：串行 10 条 964 ms（单条 96 ms），并发 10 条 499 ms，加速 **1.93x**。冷层吃的是 CPU 扫描，不是往返开销，所以加速比明显低于热层——这正好说明"加速比高低取决于瓶颈在哪"，不能一概而论。

> 20/40 并发反而比串行更快，是因为这 10 条查询本身只要 20 ms 一条，串行时被 HTTP 往返的固定开销一点点累加；并发把它们压进同一批。这说明此时瓶颈已经不是计算，是往返次数。

3.0x 是 7 轮复测的中位水平，不是天花板：单次查询的耗时波动很大（12~2074 ms 都出现过，后者是查询改写在抢 CPU），所以加速比在 2x~22x 之间飘。**别拿单次跑出来的倍数当结论**，要跑三轮以上取中位。但真正要守住的不是倍数，而是"请求不再被拒"——从报错变成排队做完，这才是这条要求的底线价值。

**测试必须用强查询，并先预热**：弱查询会触发"查询改写"（一次多跑 4 个变体，单次 2~3 秒），一个弱查询混进 10 条里就能把整组串行耗时抬高十几倍，测出来的加速比全是假的。我们的第一版就是这么测出 2.4x 的——不是因为并发不行，是因为 10 条里混了一条要跑 3 秒的。做法：先逐条跑一遍，确认返回里 `rewrite` 字段为空，再开始计时。

> 这一条同时回答了一个设计问题：**为什么不用 sqlite-vec 之类的外部向量库**。外部库有自己的连接池、自己的锁、自己"单通道"的限制，出问题时你既改不了它、也看不清它在等什么。自己扫确实慢一点——冷层 8 万条单条 96 ms、10 条并发 499 ms（加速只有 1.93x，因为瓶颈是 CPU 扫 8 万条，不是 IO）——但对个人用户够用，而且每一行代码都能查。**拿 1.93x 换"出事能自己查"，值。**

### 7. 向量要不要量化（实测结论：可以压，但别指望提速）

**结论先说：int8 量化能把磁盘砍到 1/4，精度几乎不掉，但检索一秒都不会变快。** 要不要上，取决于你缺的是空间还是时间。

实测环境：81,609 条 × 512 维，float32 全精度 159.4 MB。做法是每条向量单独一个 scale（per-vector scale），压成 int8 + 1 个 float32 缩放因子：

| 指标 | 结果 |
|:--|:--|
| float32 体积 | 159.4 MB |
| int8 + scale 体积 | 40.2 MB |
| 压缩比 | 3.97x |
| Top10 平均重合率 | 99.2% |
| Top1 一致率 | 100%（12/12） |
| 检索耗时 | float32 75 ms vs int8 77 ms |
| 量化一次性耗时 | 434 ms |

12 条查询里只有 1 条（`NAS 备份`）Top10 掉到 9/10，其余全是 10/10。

**为什么速度没变快**：现在瓶颈是 CPU 做点积，不是内存带宽。8 万条 × 512 维的 float32 数据是 159 MB，扫一遍的时间主要花在乘加运算上；换成 int8 只省了读取字节数，运算量几乎没变，还要多一步"乘回 scale"。

**再补一组关键实测（10 万条 × 5 轮均值）**：float32 零拷贝视图扫描 **55 ms**，int8 连续视图 + scale 扫描 **55 ms**，**完全一样快**。所以 int8 不是"慢一点换空间"，而是**白拿 3/4 的内存**——读路径上它几乎没有任何代价。这一条推翻了"量化会拖慢检索"的直觉，也是我们决定把它做成开关的前提。

**v0.2 的决定**：

- 默认**不量化**，直接存 float32。理由不是"更快"，而是**写入路径少一个会出错的地方**（见 7.2）
- 把量化做成**可选开关**，文档如实写：**省 3/4 内存和磁盘，检索速度基本不变**
- **无论选哪种，向量都必须带 id**（见第三节），不能靠行号对齐
- 换量化方式 = 换索引格式，必须整库重算，不能混存

> 顺带纠正一个我们自己的错误记录：早前写"87 MB 说明做过压缩或量化"是错的。那次按 768 维算的，实际模型是 bge-small-zh-v1.5，**512 维**：43690 × 512 × 4 = 85.3 MB，和文件大小对得上。全精度不是谁选的，是 float32 直接落盘的自然结果。

### 7.1 迁移友好性：int8 能不能直接发给用户（实测）

**先说结论：能上，但前提是"格式自描述 + 能双向换算"。** int8 本身不是迁移障碍，真正的障碍是下面这条我们**已经踩到**的问题。

**三种迁移路径实测（81,609 条 × 512 维）**：

| 路径 | 要不要跑模型 | 实测耗时 | 说明 |
|:--|:--|:--|:--|
| float32 → int8 | 不用 | **431 ms** | 纯本地算术，0.4 秒做完 |
| int8 → float32 | 不用 | **114 ms** | 反量化，平均误差 0.0007，最大 0.0017 |
| 从原文重算向量 | **要** | **22 分钟**（单条 16.5 ms 串行） | 兜底路径，慢但永远可用 |

**关键点：只要原文还在，向量永远可以重算。** 向量是派生数据，不是原始资产。这就是为什么 v0.2 把"原文存档"放在最底层、并且禁止改写原文——它不是洁癖，是**迁移的最后一道保险**。哪怕有一天模型全换了、量化格式全变了，只要原文还在，22 分钟就能重建一套新的。

**额外实测**：int8 反量化后模长仍是 1.000±0.0033（最大偏差 0.33%），所以"归一化向量直接点积 = 余弦相似度"这个优化在 int8 下仍然成立，不需要改成先算模长。

#### ⚠️ 真正的迁移坑：向量文件里没有记"这是哪个模型算的"

我们查了自己的两个向量文件，**两个都没记模型身份**：

| 文件 | 现有字段 | 缺什么 |
|:--|:--|:--|
| `archive_meta.json` | `files` / `dim` / `count` / `entries` | 没有模型名、没有归一化标记、没有量化格式 |
| 主库索引区 | 只有向量 + 区块名 + 锚点 | 同上 |

**这不是理论风险，它已经害过我们一次**：我之前看到 86.9 MB 就推断"做过量化或压缩"，结果按 768 维去算，全错。真实是 512 维的 float32。**当时如果有人把模型从 `bge-small-zh` 换成一个"同样是 512 维"的别的模型，文件大小不变、维度校验也全过、程序一声不响，检索结果全变成噪音。** 维度校验只能挡住"维度不同"，挡不住"维度相同但语义空间不同"。

**v0.2 硬性要求（每个向量文件必须自带这几行）**：

```json
{
  "format": "vokab-vector-v1",
  "model": "BAAI/bge-small-zh-v1.5",
  "model_sha": "7999e1d3...",
  "dim": 512,
  "normalized": true,
  "dtype": "int8",
  "scale_mode": "per-vector",
  "count": 81609
}
```

**启动时必须校验，不一致就拒绝加载并明确报错**，不能"先跑起来再说"。报错信息要写清楚怎么修：`向量是用 X 模型生成的，当前配置是 Y，请跑 rebuild-index 重建`。

**这一条的成本几乎为零**（几十个字节），但它决定了用户换模型时是"收到一句人话提示"还是"检索悄悄烂掉、几个月后才发现"。

#### 迁移场景对照（用户实际会遇到什么）

| 用户的动作 | 需要做什么 | 代价 |
|:--|:--|:--|
| float32 换 int8，不换模型 | 就地换算 | **0.4 秒** |
| int8 换 float32，不换模型 | 就地反量化 | **0.1 秒** |
| 换模型（维度也变了） | 从原文重算 | 22 分钟 / 8 万条 |
| 换模型（维度恰好相同） | **必须靠上面的 `model` 字段拦住**，然后从原文重算 | 22 分钟 |
| 换机器 / 换系统 | 只搬原文 JSONL，向量重算 | 22 分钟，且**与平台无关** |

> 最后一行是重点：**原文是纯 JSONL，任何机器、任何系统、任何语言都能读。** 向量是二进制的、依赖模型的、依赖字节序的，天生不可移植。所以 v0.2 的迁移单位永远是"原文"，不是"向量"。用户搬家用的是那 21.8 MB 的 JSON，不是 159 MB 的 bin。

**v0.2 的最终决定**：

- int8 **可以发给用户**，但必须满足：文件头自描述 + 支持双向换算 + 原文随时可重算
- 默认仍建议 float32（**结构更简单，少一类静默错误**，见 7.2），int8 留给"内存确实不够"的用户——判断依据是可用内存，不是条数
- **禁止只发向量不发原文**。只给 bin 不给 JSON，等于把用户锁死在你的模型上

### 7.2 "心智负担"到底指什么（把话说具体）

我先前说"float32 少一层心智负担"，这话太虚。实测之后可以说明白，它其实是**四个具体的地方，量化版每处都多一个必须写对的判断**：

| # | 多出来的东西 | float32 | int8 | 写错的后果 |
|:--|:--|:--|:--|:--|
| 1 | 向量从哪结束 | 一个数字：条数 = 文件字节 / (dim×4) | 要同时确认 q8 条数 = scale 条数 | 反推出来的条数是错的，读出一堆零向量 |
| 2 | 追加时写几个文件 | 1 次 append，1 个文件 | **2 次写、2 个文件**（q8 + scale），且必须先算 scale | 实测：q8 写成功、scale 写失败 → 1001 条向量只有 1000 个 scale，**第 1001 条读出来是 0 分，不报错** |
| 3 | 反量化谁负责 | 不需要，读出来就是数 | 每个读的地方都要乘一次 scale，**漏一处就静默错** | 某条检索路径分数偏低，不报错，只是"这条总也搜不到" |
| 4 | 换格式怎么算 | 就地覆盖 | 必须能双向换算 + 记住当前是哪种 | 混存之后程序不知道自己在读什么 |

**第 2 条是真正的坑，而且是我们亲手测出来的**：量化向量必须"q8 和 scale 同步追加"。两次写盘中间崩溃、或者两个进程同时追加，都会让两个文件错位。**错位之后不报错**——多出来的那条向量会拿一个不存在（或错位）的 scale 去解码，算出来的分数是垃圾，但排序照常进行，用户只会觉得"某些内容就是搜不到"。这类静默错误正是我们整套设计里最想避免的。

float32 只有一个文件、一条记录、一次写，**结构上就不存在"两边对不上"这个失败模式**。

**所以 v0.2 的真实取舍不是"快 vs 慢"（实测两者一样快），而是**：

- float32：**结构更简单**，少一类静默错误，代价是 4 倍内存
- int8：**省 3/4 内存**，代价是必须把"同步追加"这件事做对

**结论**：默认 float32 是因为它更不容易写错，不是因为 int8 慢。量化留给"内存确实不够"的用户，并且实现上**必须用交错单文件**（512 字节 int8 + 4 字节 scale 连续存放），从结构上消灭"两个文件错位"这个失败模式。**这个方案读性能不掉速**：载入时反交错一次（56 ms / 8 万条），之后扫描与 float32 打平（44 ms vs 44 ms）。详见 7.4。

> 更正：我先前说过"数据超过 50 万条再上 int8"，**这句没有实测依据，撤回**。真正该看的不是条数，而是用户机器的可用内存：索引常驻大小 ≈ 条数 × dim × 4 字节。实测读 162 MB 索引，进程 RSS 涨 278 MB（约等于文件大小，没有放大倍数）。32 GB 内存的机器，float32 撑到 100 万条（1.9 GB）毫无压力；8 GB 的机器，20 万条（390 MB）就该考虑量化了。

### 7.3 量化精度的真实边界（一条会被翻转的查询）

12 条查询里 Top1 全对、Top10 重合 99.2%，看起来像"无损"。但换一组查询实测，**Top1 一致率掉到 91.7%**（12 条里错 1 条）。

差别不在精度，在**分数差距**：唯一翻转的那条，Top1 只比第二名高 **0.0009**。

| Top1 领先第二名 | 条数 | 是否翻转 |
|:--|:--|:--|
| < 0.001（几乎并列） | 1 | **翻转** |
| 0.005 ~ 0.01 | 4 | 不翻转 |
| > 0.01 | 7 | 不翻转 |

**结论：int8 的误差量级约 0.001~0.002，只有当两条结果本身几乎并列时才会改变排序。** 并列时谁第一本来就没有意义，所以这个翻转不算质量问题。

**但验收时必须这样测**，否则会得出错误结论：只测"强查询"（分数差距大）会得到 100%，只测"弱查询"会得到 91.7%，**两个都不代表真实水平**。正确做法是记录"Top1 领先第二名多少"，把结果按分数差距分档报告。

### 7.4 追加写 2 次 vs 转换写 1 次（把两件事分清楚）

上一版我把两个不同阶段搅在一起说了，这里分开讲清楚。

**阶段一：一次性把 float32 转成 int8（迁移时做一次）**

| 方案 | 写盘次数 | 量化计算 | 写盘 | 合计 |
|:--|:--|:--|:--|:--|
| q8 / scale 两个文件 | 2 次 | 419 ms | **22 ms** | 441 ms |
| 交错单文件 | **1 次** | 419 ms | **22 ms** | 493 ms（多 52 ms 打包） |

两种方案写盘都只是 **22 ms**——因为输出只有 40 MB。"2 次"指的是两次系统调用，不是两份时间。**所以"要不要写 2 次"这个顾虑，在转换阶段几乎不存在。**

**阶段二：之后每追加一条新向量，才是真正要区分的**

| 方案 | 每条追加 | 崩溃/并发风险 |
|:--|:--|:--|
| float32 | 1 次 append | 无（一条记录原子） |
| int8 两文件 | **2 次 append**（q8 一次、scale 一次） | **有**：两次之间失败会错位，且错位后不报错 |
| int8 交错单文件 | **1 次 append**（516 字节一条） | 无（同 float32） |

这才是 7.2 说的"心智负担"真正所在：**不是转换，是日常追加。**

**交错单文件的读性能实测（81,609 条）**：

| 读法 | 单次扫描 | 相对 float32 |
|:--|:--|:--|
| float32 零拷贝视图 | 44 ms | 基准 |
| 交错 · 每次逐字节解码 | 59 ms | 1.33x 慢 |
| **交错 · 载入时反交错一次** | **44 ms** | **1.00x，打平** |

反交错（把 516 字节拆成连续的 int8 数组 + scale 数组）一次性只要 **56 ms**，之后扫描完全不打折。**所以"交错会慢 1.3 倍"只在偷懒逐字节解码时成立，正确实现是零代价。**

**最终格式约定（v0.2 定）**：

```
每条记录固定 516 字节：
  [0, 512)     512 个 int8   量化后的向量分量
  [512, 516)   1 个 float32  该向量的 scale（小端）
```

- 追加 = 往文件尾写 516 字节，**一次 write**
- 条数 = 文件字节 / 516，**不需要旁挂 scale 文件**
- 载入 = 一次读全文件 + 一次反交错（56 ms / 8 万条）
- 崩溃/并发 = 不会错位（一条记录要么完整要么没有）

**另一种可选：整个库只用一个 scale**（连 4 字节都省掉）。实测代价明显：

| scale 方案 | Top10 重合 | Top1 一致 | 存储 |
|:--|:--|:--|:--|
| 每条一个（per-vector） | **99.2%** | **100%** | 每条 4 B |
| 全库固定 0.44 | 97.5% | 100% | 文件头 1 个 float |
| 全库固定 0.349 | 95.0% | 91.7% | 文件头 1 个 float |
| 全库固定 0.30 | 90.0% | 83.3% | 文件头 1 个 float |

原因是每个向量的最大分量在 0.236~0.407 之间浮动（1.72 倍差异），全库一个 scale 就等于**按最大的那个来定步长，小向量白白损失分辨率**。每条 4 字节换 2~7 个百分点的重合率，**不值当省**。所以定：**每条一个 scale**。

### 7.5 格式定案：XVEC v1（一条一次写，带 id，自带模型标识）

上一步把"要不要 2 次写"分清楚了。这里定死格式，因为**格式一旦发出去，用户的数据就在里面了，再改就要用户迁移**。

**设计原则：一个失败模式都不留。**

| 失败模式 | 怎么消掉 |
|:--|:--|
| 两个文件错位 | ❌ 不存在——只有**一个文件**，一条记录自包含 |
| 写一半断电 | ✅ 整条记录要么在、要么不在（余数字节立刻可检测） |
| 多进程同时写撕裂 | ✅ 实测 16 进程 × 1000 条 = 16000 条，0 条撕裂 |
| 删改一条后面全错位 | ✅ 每条带 id，不靠序号定位 |
| 换了模型没发现 | ✅ 文件头记模型 SHA，对不上直接拒绝加载 |
| 读到一半发现坏了 | ✅ 头部先校验，坏文件在打开时报错，不会静默 |

#### 字节布局

```
文件 = 64 字节头 + N 条记录（每条 524 字节）

头部（64 B）
  [0,4)     "XVEC"          魔数
  [4,6)     u16 版本         = 1
  [6,8)     u16 已归一化     1=是（可直接点积当余弦）
  [8,10)    u16 维度         512
  [10,12)   u16 保留         0
  [12,14)   u16 记录长度     524
  [14,16)   u16 保留         0
  [16,48)   32 字节         模型标识（sha256(模型名字符串) 前 32 字节）
  [48,64)   16 字节         保留（预留量化方式等扩展）

记录（524 B）
  [0,512)   512 个 int8     量化后的向量分量（-127~127）
  [512,516) float32 小端    scale（该向量的量化步长）
  [516,524) uint64 小端     id（与原文记录一一对应）
```

**为什么不用变长编码、不用 JSON**：变长意味着每条长度不同，就必须有"下一条从哪开始"的索引，于是又回到"两个东西要对齐"的老问题。**固定长度是这套格式能"一条一次写"的根本原因。**

#### 实测数据（81,609 条真实数据）

| 指标 | 结果 |
|:--|:--|
| 转换 float32 → XVEC | **519 ms** |
| 体积 | 159.4 MB → **40.8 MB（25.6%）** |
| 载入（读文件 + 反交错） | **76 ms** |
| 平均误差 / 最大误差 | 0.000654 / 0.001583 |
| Top10 重合 / Top1 一致 | **99.2% / 100%** |

#### 安全验证（全部实测，不是推理）

| 场景 | 结果 |
|:--|:--|
| 8 进程 × 500 条并发追加 | 5000 条，0 撕裂 ✅ |
| 16 进程 × 1000 条并发追加 | 16000 条，0 撕裂 ✅ |
| 模拟断电（截掉尾部 300 B） | 检测到 224 B 残缺，**立刻报错** ✅ |
| 截尾修复后 | 4999 条完整，坏的那条自动丢弃 ✅ |
| 换模型后打开 | **拒绝加载**：`向量是用别的模型算的，请重建索引` ✅ |
| 维度不符 | 拒绝加载 ✅ |

#### 必须一起交付的东西

格式不是"一个文件格式"这么简单，下面四件少一个就不成立：

1. **读写库**（150 行以内，含头部校验、截断检测、反交错）
2. **从原文重建**：`rebuild-index` 命令，模型换了/格式变了都靠它兜底（8 万条 22 分钟）
3. **截断自愈**：打开时发现 `(文件大小-64) % 524 != 0`，截掉尾部残缺记录并记日志，**不要静默继续**
4. **格式版本升级路径**：`version` 字段 + `rebuild-index`，**永不做"就地转换不同版本"**

> **关于"自己开发向量格式"**：这件事不用等以后做，上面这个就是。它足够小（524 字节一条）、足够简单（固定长度、纯追加）、足够安全（一条一次写、带 id、带模型标识）。**但它只在 v0.2 里定死，星核现用的 `archive_vectors.bin` 不改**——那是生产数据，改格式要配合迁移，不能顺手做。

## 五、回流防护（三层）

1. 召回注入内容带 `[记忆]` 前缀，提炼时整段剔除
2. 新内容与最近召回相似度 >0.9 且同会话 → 判复述
3. `origin=recall_echo` 不参与后续召回

### 隐私警告（写清楚，不设机制）

**这部分明确不做技术拦截。** 用户的记忆库就是他的仓库，密码、密钥、身份证号天然会进去，做拦截既拦不住，还会把真实内容变得残缺。

编写规范里必须用醒目段落写：

> ⚠️ **请勿粘贴密码、密钥、银行卡号、身份证号等敏感信息。**
> 记忆库是明文存储、明文检索的。一旦写入，它会和普通对话一样被长期保存、被语义检索召回、被 AI 读进上下文。
> 我们不做自动脱敏、不做加密、不做敏感词过滤——因为那样会破坏"原文一个字不改"这条底线。
> 这件事只能靠你自己把关。

同时写一句诚实的补充：这只是一条警告，不是保护。用户如果坚持要存，系统会照存。

## 八、提炼失败：先查为什么会失败，再谈怎么办

**这一节的结论来自真实日志，不是推演。** 我们本来打算设计"重试几次放弃、放弃后怎么标记"的机制，后来先去看历史失败记录，发现方向错了。

#### 实测：失败只有 1 次，而且自己好了

在 20 多天的运行日志里，`提炼未成功` 只出现 1 次：

```
[守护] 名单取钥失败，用旧密码兜底: The operation was aborted due to timeout
[守护] ① 读编写规范...
[守护] 提炼未成功，不标记完成（下次空闲会补炼）
```

**失败点在第 ① 步：读编写规范。还没走到调用模型。** 下一轮同样的目标日期，直接成功了。

所以真实失败只有一个原因：**本机接口超时**。不是模型返回格式错误，不是内容非法，不是余额不足。

#### 失败阶段分布（按代码路径排）

| 阶段 | 失败原因 | 是否需要重试 | 实际出现过 |
|:--|:--|:--|:--|
| ① 读编写规范 | 本机接口超时 | 是，但应该快速重试 | ✅ 1 次 |
| ② 读前一天月轴 | 本机接口超时 | 是 | 无 |
| ③ 读对话存档 | 文件读不到 | 是 | 无 |
| ④ 调模型 | 网络/余额/格式 | 是 | 无 |
| ⑤ 写入月轴 | 写锁冲突 | 是 | 无 |

#### 由此推出的三条原则

**原则一：本机接口失败，不适用模型退避。**

本机接口（`/api/v1/spec/full`、`/api/v1/day`、`/recall`）正常是毫秒级。等到 5 秒说明引擎那边有问题。这时候：

- **连模型都没调**，谈不上"模型提炼失败"
- 用 5 分钟起步的指数退避，只会把重试越推越远
- 应该是固定 60 秒重试——引擎恢复就立刻能跑

**原则二：失败必须记"卡在哪一步"，不能只记"失败了"。**

原来只写一句 `提炼未成功`。事后不看日志就永远不知道是①、③还是④。状态文件里必须有三样：

```json
{
  "refineFailStage": "①读编写规范失败",
  "refineFailReason": "local:...timeout",
  "refineFailLocal": true
}
```

**原则三：不要一开始就设计"放弃机制"。**

我们原本打算做"连续失败 5 次就放弃这一天、推进游标"。**这个设计是错的**，理由：

- 推进游标等于"以后不再自动处理这天"，是**数据静默消失**的唯一入口
- 而真实失败全是瞬时故障，自己会好
- 为了一个没发生过的风险，引入一个会造成永久损失的操作，不划算

**如果以后真出现永久失败**（模型一直返回非法格式），再单独设计。届时的前提是：原始对话必须确认完整 + 放弃记录可查 + 可手动补炼。

#### v0.2 的要求

| # | 要求 |
|:--|:--|
| 1 | 每个阶段失败都要带上阶段名，写进状态文件 |
| 2 | 区分"本机接口失败"和"模型失败"，前者用短重试（60 秒），后者用指数退避 |
| 3 | 本机接口超时不超过 5 秒（正常是毫秒级，5 秒已经说明有问题） |
| 4 | 取钥这类"尽力而为"的请求，超时不超过 2 秒，且成功后有缓存期 |
| 5 | **不实现"连续失败放弃机制"**，除非出现真实的永久失败案例 |
| 6 | 失败绝不推进游标——原始对话必须保留，下一轮重试 |

**验收方式**：人为让本机接口不可用（改端口），触发提炼，检查状态文件是否记录了正确阶段和 `local: true`，且重试间隔是 60 秒而不是 5 分钟。

## 九、明确不做 / 不支持（v0.2）

| 项 | 决定 |
|:--|:--|
| 多租户 | ❌ 不做。只面向个人用户 |
| 删除记忆 | ❌ 不支持。记忆是存证，违背原则 |

| 向量格式跨版本就地转换 | ❌ 不做。换版本一律从原文重建，避免"半新半旧"的混合文件 |

| 本机接口失败走模型退避 | ❌ 不做。连模型都没调，退避只会把重试越推越远，应该 60 秒快速重试 |

## 十、MVP 与测试计划

**MVP**：草稿 → 提炼 → 入库 → 召回 全链路最小实现 + 校验器 15 项 + 回流防护 + 验收单。

**测试用例约 25 个**，每条坑至少一个：
正常写入/召回、乱码、重复（导入层内容判重 + 草稿层身份去重，两层分开测）、回流、错位、粘连、伪块、embed 失败、游标失效、时区、空内容、格式漂移、上下文窗口、时间过滤、超大内容、草稿生命周期、提炼失败重试、链网写入校验、退出强制落库、验收单五项。

**测试完清空全部数据，出 `TEST-REPORT.md`**（每坑：现象→复现→防护→验证）。

**并发用例必须有**：至少一个"高并发打检索"的用例，验证 32 并发 0 拒连、结果一致。这条容易被漏掉，因为单线程测试永远发现不了。

**性能验收单（必须实测，不接受"应该很快"）**：

| # | 项 | 合格判据 |
|:--|:--|:--|
| 1 | 单日归档 | < 10 秒（星核修完是 4.71 秒） |
| 2 | 单日重建索引 | < 15 秒（按 383 条算约 9 秒） |
| 3 | 性能改动输出不变 | 新旧版本对同一天各跑一次，输出 SHA1 全同、条目逐条相同 |
| 4 | JOIN 查询 | `EXPLAIN QUERY PLAN` 无意外全局 `SCAN`，并在报告里贴出计划 |
| 5 | 检索并发 | 并发 32 条同时打，成功率 100%（0 个连接被拒）；同查询并发 12 次，结果签名完全一致 |
| 6 | 并发不劣化 | 并发 10 条的耗时明显低于串行 10 条；报告里附串行/并发两组实测数字 |
| 7 | 量化（若启用） | Top1 一致率 ≥ 99%，Top10 重合率 ≥ 98%，并如实写明"是否提速" |
| 8 | 格式可迁移 | float32↔int8 双向换算各 < 1 秒；从原文全量重算 < 60 分钟；向量文件头含模型名与模型 SHA |
| 9 | 并发追加不撕裂 | 16 进程同时追加 16000 条，条数准确、0 撕裂、0 错位 |
| 10 | 截断可自愈 | 人为截掉尾部 300 B，打开时可检测并截尾到整数条，坏记录被丢弃且记日志 |
| 11 | 错模型必拒 | 用不同模型名打开，必须抛出可读错误，不得静默加载 |
| 12 | 失败可诊断 | 人为让本机接口不可用，状态文件须记录正确阶段名与 `local:true`，且重试间隔为 60 秒（非 5 分钟） |
