## 一、Python 侧教训

### 1. 禁止用 `bytes += chunk` 拼接

**坑**：解压 DSH 会话包（21.3 MB 压缩 → 48.6 MB 原文），代码是：

```python
raw = b""
while True:
    chunk = reader.read(65536)
    if not chunk: break
    raw += chunk          # ← 这里
```

bytes 在 Python 里不可变，每加一次就把已有内容整份复制一遍。48.6 MB 拼了约 740 次，实际是 O(n²)。

**实测代价**：这段解压 **328.9 秒**，占掉单日归档 67 秒里的 63 秒。换成 `chunks.append(chunk)` + `b"".join(chunks)` 后 **0.2 秒**，**快 1486 倍**，输出逐字节相同。

**规则**：任何"循环里往 bytes / 字符串上累加"的写法，一律改成"收集到列表 + 最后一次 join"。这条同样适用于 JavaScript（`str += x` 在 V8 有 rope 优化，相对安全，但大循环仍然别赌）。

### 2. JOIN 必须验执行计划

**坑**：从 ZCode 的 SQLite 取当天消息：

```sql
SELECT m.id, m.time_created, m.data, p.data
FROM message m JOIN part p ON p.message_id = m.id
WHERE m.time_created >= ? AND m.time_created <= ?
ORDER BY m.time_created ASC
```

看起来完全正常。但 `EXPLAIN QUERY PLAN` 显示它 **`SCAN p`** —— 先全表扫 part 的 19.7 万行，再逐行回查 message。**7091 ms**。

改成 `CROSS JOIN` 强制以 message 为驱动表：

```sql
FROM message m CROSS JOIN part p
WHERE p.message_id = m.id
  AND m.time_created >= ? AND m.time_created <= ?
```

走 `message_session_time_created_id_idx` 再按 `part_message_sequence_idx` 取子行，**155 ms，快 45 倍**，670 行结果逐条比对完全一致。

**规则**：任何带 JOIN 的查询，上线前必须跑一次 `EXPLAIN QUERY PLAN`，确认没有意外的全表 `SCAN`。SQLite 的优化器不看你"想让它怎么跑"。


## 二、向量量化与 XVEC（未来优化）

### 7. 向量要不要量化（实测结论：可以压，但别指望提速）

**结论先说：int8 量化能把磁盘砍到 1/4，精度几乎不掉，但检索一秒都不会变快。** 要不要上，取决于你缺的是空间还是时间。

实测环境：81,609 条 × 512 维，float32 全精度 159.4 MB。做法是每条向量单独一个 scale（per-vector scale），压成 int8 + 1 个 float32 缩放因子：

| 指标 | 结果 |
|:--|:--|
| float32 体积 | 159.4 MB |
| int8 + scale 体积 | 40.2 MB |
| 压缩比 | 3.97x |
| Top10 平均重合率 | 99.2% |
| Top1 一致率 | 100%（12/12） |
| 检索耗时 | float32 75 ms vs int8 77 ms |
| 量化一次性耗时 | 434 ms |

12 条查询里只有 1 条（`NAS 备份`）Top10 掉到 9/10，其余全是 10/10。

**为什么速度没变快**：现在瓶颈是 CPU 做点积，不是内存带宽。8 万条 × 512 维的 float32 数据是 159 MB，扫一遍的时间主要花在乘加运算上；换成 int8 只省了读取字节数，运算量几乎没变，还要多一步"乘回 scale"。

**再补一组关键实测（10 万条 × 5 轮均值）**：float32 零拷贝视图扫描 **55 ms**，int8 连续视图 + scale 扫描 **55 ms**，**完全一样快**。所以 int8 不是"慢一点换空间"，而是**白拿 3/4 的内存**——读路径上它几乎没有任何代价。这一条推翻了"量化会拖慢检索"的直觉，也是我们决定把它做成开关的前提。

**v0.2 的决定**：

- 默认**不量化**，直接存 float32。理由不是"更快"，而是**写入路径少一个会出错的地方**（见 7.2）
- 把量化做成**可选开关**，文档如实写：**省 3/4 内存和磁盘，检索速度基本不变**
- **无论选哪种，向量都必须带 id**（见第三节），不能靠行号对齐
- 换量化方式 = 换索引格式，必须整库重算，不能混存

> 顺带纠正一个我们自己的错误记录：早前写"87 MB 说明做过压缩或量化"是错的。那次按 768 维算的，实际模型是 bge-small-zh-v1.5，**512 维**：43690 × 512 × 4 = 85.3 MB，和文件大小对得上。全精度不是谁选的，是 float32 直接落盘的自然结果。

### 7.1 迁移友好性：int8 能不能直接发给用户（实测）

**先说结论：能上，但前提是"格式自描述 + 能双向换算"。** int8 本身不是迁移障碍，真正的障碍是下面这条我们**已经踩到**的问题。

**三种迁移路径实测（81,609 条 × 512 维）**：

| 路径 | 要不要跑模型 | 实测耗时 | 说明 |
|:--|:--|:--|:--|
| float32 → int8 | 不用 | **431 ms** | 纯本地算术，0.4 秒做完 |
| int8 → float32 | 不用 | **114 ms** | 反量化，平均误差 0.0007，最大 0.0017 |
| 从原文重算向量 | **要** | **22 分钟**（单条 16.5 ms 串行） | 兜底路径，慢但永远可用 |

**关键点：只要原文还在，向量永远可以重算。** 向量是派生数据，不是原始资产。这就是为什么 v0.2 把"原文存档"放在最底层、并且禁止改写原文——它不是洁癖，是**迁移的最后一道保险**。哪怕有一天模型全换了、量化格式全变了，只要原文还在，22 分钟就能重建一套新的。

**额外实测**：int8 反量化后模长仍是 1.000±0.0033（最大偏差 0.33%），所以"归一化向量直接点积 = 余弦相似度"这个优化在 int8 下仍然成立，不需要改成先算模长。

#### ⚠️ 真正的迁移坑：向量文件里没有记"这是哪个模型算的"

我们查了自己的两个向量文件，**两个都没记模型身份**：

| 文件 | 现有字段 | 缺什么 |
|:--|:--|:--|
| `archive_meta.json` | `files` / `dim` / `count` / `entries` | 没有模型名、没有归一化标记、没有量化格式 |
| 主库索引区 | 只有向量 + 区块名 + 锚点 | 同上 |

**这不是理论风险，它已经害过我们一次**：我之前看到 86.9 MB 就推断"做过量化或压缩"，结果按 768 维去算，全错。真实是 512 维的 float32。**当时如果有人把模型从 `bge-small-zh` 换成一个"同样是 512 维"的别的模型，文件大小不变、维度校验也全过、程序一声不响，检索结果全变成噪音。** 维度校验只能挡住"维度不同"，挡不住"维度相同但语义空间不同"。

**v0.2 硬性要求（每个向量文件必须自带这几行）**：

```json
{
  "format": "vokab-vector-v1",
  "model": "BAAI/bge-small-zh-v1.5",
  "model_sha": "7999e1d3...",
  "dim": 512,
  "normalized": true,
  "dtype": "int8",
  "scale_mode": "per-vector",
  "count": 81609
}
```

**启动时必须校验，不一致就拒绝加载并明确报错**，不能"先跑起来再说"。报错信息要写清楚怎么修：`向量是用 X 模型生成的，当前配置是 Y，请跑 rebuild-index 重建`。

**这一条的成本几乎为零**（几十个字节），但它决定了用户换模型时是"收到一句人话提示"还是"检索悄悄烂掉、几个月后才发现"。

#### 迁移场景对照（用户实际会遇到什么）

| 用户的动作 | 需要做什么 | 代价 |
|:--|:--|:--|
| float32 换 int8，不换模型 | 就地换算 | **0.4 秒** |
| int8 换 float32，不换模型 | 就地反量化 | **0.1 秒** |
| 换模型（维度也变了） | 从原文重算 | 22 分钟 / 8 万条 |
| 换模型（维度恰好相同） | **必须靠上面的 `model` 字段拦住**，然后从原文重算 | 22 分钟 |
| 换机器 / 换系统 | 只搬原文 JSONL，向量重算 | 22 分钟，且**与平台无关** |

> 最后一行是重点：**原文是纯 JSONL，任何机器、任何系统、任何语言都能读。** 向量是二进制的、依赖模型的、依赖字节序的，天生不可移植。所以 v0.2 的迁移单位永远是"原文"，不是"向量"。用户搬家用的是那 21.8 MB 的 JSON，不是 159 MB 的 bin。

**v0.2 的最终决定**：

- int8 **可以发给用户**，但必须满足：文件头自描述 + 支持双向换算 + 原文随时可重算
- 默认仍建议 float32（**结构更简单，少一类静默错误**，见 7.2），int8 留给"内存确实不够"的用户——判断依据是可用内存，不是条数
- **禁止只发向量不发原文**。只给 bin 不给 JSON，等于把用户锁死在你的模型上

### 7.2 "心智负担"到底指什么（把话说具体）

我先前说"float32 少一层心智负担"，这话太虚。实测之后可以说明白，它其实是**四个具体的地方，量化版每处都多一个必须写对的判断**：

| # | 多出来的东西 | float32 | int8 | 写错的后果 |
|:--|:--|:--|:--|:--|
| 1 | 向量从哪结束 | 一个数字：条数 = 文件字节 / (dim×4) | 要同时确认 q8 条数 = scale 条数 | 反推出来的条数是错的，读出一堆零向量 |
| 2 | 追加时写几个文件 | 1 次 append，1 个文件 | **2 次写、2 个文件**（q8 + scale），且必须先算 scale | 实测：q8 写成功、scale 写失败 → 1001 条向量只有 1000 个 scale，**第 1001 条读出来是 0 分，不报错** |
| 3 | 反量化谁负责 | 不需要，读出来就是数 | 每个读的地方都要乘一次 scale，**漏一处就静默错** | 某条检索路径分数偏低，不报错，只是"这条总也搜不到" |
| 4 | 换格式怎么算 | 就地覆盖 | 必须能双向换算 + 记住当前是哪种 | 混存之后程序不知道自己在读什么 |

**第 2 条是真正的坑，而且是我们亲手测出来的**：量化向量必须"q8 和 scale 同步追加"。两次写盘中间崩溃、或者两个进程同时追加，都会让两个文件错位。**错位之后不报错**——多出来的那条向量会拿一个不存在（或错位）的 scale 去解码，算出来的分数是垃圾，但排序照常进行，用户只会觉得"某些内容就是搜不到"。这类静默错误正是我们整套设计里最想避免的。

float32 只有一个文件、一条记录、一次写，**结构上就不存在"两边对不上"这个失败模式**。

**所以 v0.2 的真实取舍不是"快 vs 慢"（实测两者一样快），而是**：

- float32：**结构更简单**，少一类静默错误，代价是 4 倍内存
- int8：**省 3/4 内存**，代价是必须把"同步追加"这件事做对

**结论**：默认 float32 是因为它更不容易写错，不是因为 int8 慢。量化留给"内存确实不够"的用户，并且实现上**必须用交错单文件**（512 字节 int8 + 4 字节 scale 连续存放），从结构上消灭"两个文件错位"这个失败模式。**这个方案读性能不掉速**：载入时反交错一次（56 ms / 8 万条），之后扫描与 float32 打平（44 ms vs 44 ms）。详见 7.4。

> 更正：我先前说过"数据超过 50 万条再上 int8"，**这句没有实测依据，撤回**。真正该看的不是条数，而是用户机器的可用内存：索引常驻大小 ≈ 条数 × dim × 4 字节。实测读 162 MB 索引，进程 RSS 涨 278 MB（约等于文件大小，没有放大倍数）。32 GB 内存的机器，float32 撑到 100 万条（1.9 GB）毫无压力；8 GB 的机器，20 万条（390 MB）就该考虑量化了。

### 7.3 量化精度的真实边界（一条会被翻转的查询）

12 条查询里 Top1 全对、Top10 重合 99.2%，看起来像"无损"。但换一组查询实测，**Top1 一致率掉到 91.7%**（12 条里错 1 条）。

差别不在精度，在**分数差距**：唯一翻转的那条，Top1 只比第二名高 **0.0009**。

| Top1 领先第二名 | 条数 | 是否翻转 |
|:--|:--|:--|
| < 0.001（几乎并列） | 1 | **翻转** |
| 0.005 ~ 0.01 | 4 | 不翻转 |
| > 0.01 | 7 | 不翻转 |

**结论：int8 的误差量级约 0.001~0.002，只有当两条结果本身几乎并列时才会改变排序。** 并列时谁第一本来就没有意义，所以这个翻转不算质量问题。

**但验收时必须这样测**，否则会得出错误结论：只测"强查询"（分数差距大）会得到 100%，只测"弱查询"会得到 91.7%，**两个都不代表真实水平**。正确做法是记录"Top1 领先第二名多少"，把结果按分数差距分档报告。

### 7.4 追加写 2 次 vs 转换写 1 次（把两件事分清楚）

上一版我把两个不同阶段搅在一起说了，这里分开讲清楚。

**阶段一：一次性把 float32 转成 int8（迁移时做一次）**

| 方案 | 写盘次数 | 量化计算 | 写盘 | 合计 |
|:--|:--|:--|:--|:--|
| q8 / scale 两个文件 | 2 次 | 419 ms | **22 ms** | 441 ms |
| 交错单文件 | **1 次** | 419 ms | **22 ms** | 493 ms（多 52 ms 打包） |

两种方案写盘都只是 **22 ms**——因为输出只有 40 MB。"2 次"指的是两次系统调用，不是两份时间。**所以"要不要写 2 次"这个顾虑，在转换阶段几乎不存在。**

**阶段二：之后每追加一条新向量，才是真正要区分的**

| 方案 | 每条追加 | 崩溃/并发风险 |
|:--|:--|:--|
| float32 | 1 次 append | 无（一条记录原子） |
| int8 两文件 | **2 次 append**（q8 一次、scale 一次） | **有**：两次之间失败会错位，且错位后不报错 |
| int8 交错单文件 | **1 次 append**（516 字节一条） | 无（同 float32） |

这才是 7.2 说的"心智负担"真正所在：**不是转换，是日常追加。**

**交错单文件的读性能实测（81,609 条）**：

| 读法 | 单次扫描 | 相对 float32 |
|:--|:--|:--|
| float32 零拷贝视图 | 44 ms | 基准 |
| 交错 · 每次逐字节解码 | 59 ms | 1.33x 慢 |
| **交错 · 载入时反交错一次** | **44 ms** | **1.00x，打平** |

反交错（把 516 字节拆成连续的 int8 数组 + scale 数组）一次性只要 **56 ms**，之后扫描完全不打折。**所以"交错会慢 1.3 倍"只在偷懒逐字节解码时成立，正确实现是零代价。**

**最终格式约定（v0.2 定）**：

```
每条记录固定 516 字节：
  [0, 512)     512 个 int8   量化后的向量分量
  [512, 516)   1 个 float32  该向量的 scale（小端）
```

- 追加 = 往文件尾写 516 字节，**一次 write**
- 条数 = 文件字节 / 516，**不需要旁挂 scale 文件**
- 载入 = 一次读全文件 + 一次反交错（56 ms / 8 万条）
- 崩溃/并发 = 不会错位（一条记录要么完整要么没有）

**另一种可选：整个库只用一个 scale**（连 4 字节都省掉）。实测代价明显：

| scale 方案 | Top10 重合 | Top1 一致 | 存储 |
|:--|:--|:--|:--|
| 每条一个（per-vector） | **99.2%** | **100%** | 每条 4 B |
| 全库固定 0.44 | 97.5% | 100% | 文件头 1 个 float |
| 全库固定 0.349 | 95.0% | 91.7% | 文件头 1 个 float |
| 全库固定 0.30 | 90.0% | 83.3% | 文件头 1 个 float |

原因是每个向量的最大分量在 0.236~0.407 之间浮动（1.72 倍差异），全库一个 scale 就等于**按最大的那个来定步长，小向量白白损失分辨率**。每条 4 字节换 2~7 个百分点的重合率，**不值当省**。所以定：**每条一个 scale**。

### 7.5 格式定案：XVEC v1（一条一次写，带 id，自带模型标识）

上一步把"要不要 2 次写"分清楚了。这里定死格式，因为**格式一旦发出去，用户的数据就在里面了，再改就要用户迁移**。

**设计原则：一个失败模式都不留。**

| 失败模式 | 怎么消掉 |
|:--|:--|
| 两个文件错位 | ❌ 不存在——只有**一个文件**，一条记录自包含 |
| 写一半断电 | ✅ 整条记录要么在、要么不在（余数字节立刻可检测） |
| 多进程同时写撕裂 | ✅ 实测 16 进程 × 1000 条 = 16000 条，0 条撕裂 |
| 删改一条后面全错位 | ✅ 每条带 id，不靠序号定位 |
| 换了模型没发现 | ✅ 文件头记模型 SHA，对不上直接拒绝加载 |
| 读到一半发现坏了 | ✅ 头部先校验，坏文件在打开时报错，不会静默 |

#### 字节布局

```
文件 = 64 字节头 + N 条记录（每条 524 字节）

头部（64 B）
  [0,4)     "XVEC"          魔数
  [4,6)     u16 版本         = 1
  [6,8)     u16 已归一化     1=是（可直接点积当余弦）
  [8,10)    u16 维度         512
  [10,12)   u16 保留         0
  [12,14)   u16 记录长度     524
  [14,16)   u16 保留         0
  [16,48)   32 字节         模型标识（sha256(模型名字符串) 前 32 字节）
  [48,64)   16 字节         保留（预留量化方式等扩展）

记录（524 B）
  [0,512)   512 个 int8     量化后的向量分量（-127~127）
  [512,516) float32 小端    scale（该向量的量化步长）
  [516,524) uint64 小端     id（与原文记录一一对应）
```

**为什么不用变长编码、不用 JSON**：变长意味着每条长度不同，就必须有"下一条从哪开始"的索引，于是又回到"两个东西要对齐"的老问题。**固定长度是这套格式能"一条一次写"的根本原因。**

#### 实测数据（81,609 条真实数据）

| 指标 | 结果 |
|:--|:--|
| 转换 float32 → XVEC | **519 ms** |
| 体积 | 159.4 MB → **40.8 MB（25.6%）** |
| 载入（读文件 + 反交错） | **76 ms** |
| 平均误差 / 最大误差 | 0.000654 / 0.001583 |
| Top10 重合 / Top1 一致 | **99.2% / 100%** |

#### 安全验证（全部实测，不是推理）

| 场景 | 结果 |
|:--|:--|
| 8 进程 × 500 条并发追加 | 5000 条，0 撕裂 ✅ |
| 16 进程 × 1000 条并发追加 | 16000 条，0 撕裂 ✅ |
| 模拟断电（截掉尾部 300 B） | 检测到 224 B 残缺，**立刻报错** ✅ |
| 截尾修复后 | 4999 条完整，坏的那条自动丢弃 ✅ |
| 换模型后打开 | **拒绝加载**：`向量是用别的模型算的，请重建索引` ✅ |
| 维度不符 | 拒绝加载 ✅ |

#### 必须一起交付的东西

格式不是"一个文件格式"这么简单，下面四件少一个就不成立：

1. **读写库**（150 行以内，含头部校验、截断检测、反交错）
2. **从原文重建**：`rebuild-index` 命令，模型换了/格式变了都靠它兜底（8 万条 22 分钟）
3. **截断自愈**：打开时发现 `(文件大小-64) % 524 != 0`，截掉尾部残缺记录并记日志，**不要静默继续**
4. **格式版本升级路径**：`version` 字段 + `rebuild-index`，**永不做"就地转换不同版本"**

> **关于"自己开发向量格式"**：这件事不用等以后做，上面这个就是。它足够小（524 字节一条）、足够简单（固定长度、纯追加）、足够安全（一条一次写、带 id、带模型标识）。**但它只在 v0.2 里定死，星核现用的 `archive_vectors.bin` 不改**——那是生产数据，改格式要配合迁移，不能顺手做。
