# 测试方案：心路历程（日记）+ 自动唤醒

> 目的：把「日记能不能写、能不能回看」和「自动唤醒会不会在该醒的时候醒、该闭嘴的时候闭嘴」跑成可复现的验收，而不是只看单测。
>
> 单测是逻辑层；这份方案补的是 DSH 真实会话这一层。

## 一、已有自动化（先跑这个）

```bash
node test/unit-heart.js
node test/unit-wake.js
node test/unit-wake-care.js
node test/unit-wake-scheduler.js
node test/unit-wake-tools.js
node test/unit-wake-profile.js
```

当前结果（2026-11-15）：

| --- | --- |
| unit-heart | 48/48 |
| unit-wake | 68/68 |
| unit-wake-care | 27/27 |
| unit-wake-scheduler | 30/30 |

`test/selfcheck.js` 已把 `unit-heart.js` 补进列表（之前漏了）。

这些覆盖：开关、写盘格式 `v:1`、重复/超长拒绝、标签、按天读、预算截断、搜索、旧平铺文件；唤醒的安静时段、最小间隔、每日上限、用户刚说话、连续无回应/暂停、简报、模拟时间、提醒、日志、目标会话字段。

## 二、没覆盖的（这份方案要补）

1. DSH 里模型真的调用 `memory_heart` 写一条，常识层下一轮真的带上。
2. 到点后 `agent.followup` 真的投到**绑定的目标会话**，不是最近活跃的工作会话。
3. 唤醒消息不会被当成用户原话写进 raw/草稿。
4. 重启 DSH 后状态、排程、目标会话还在，且不重复投。
5. 日记/唤醒对「工作会话」和「陪听会话」的隔离。

## 三、前置（别动真实记忆）

- 用一份临时数据根：设 `MEMORY_ROOT` 指向空目录，或复制一份 `dsh-memory` 到临时目录再指向它。
- 用一个专门的测试会话；不要在正在办公的会话里验收自动唤醒。
- 记下测试前后的 `raw/`、`draft/pending.jsonl`、`data/heart/`、`wake/config.json`（或对应状态文件），方便对照。
- 端口不和正式实例冲突时再开总览（默认 3099）。

## 四、日记 E2E

| # | 步骤 | 期望 |
| --- | --- | --- |
| H1 | 首次进入，未设置 | 常识层提示「还没设置」；模型只问一次要不要开；拒绝后不再提 |
| H2 | 关闭状态调用 `memory_heart write` | 拒绝，`reason=disabled`；不落盘 |
| H3 | `memory_heart enable` 后写一条 | `data/heart/年/月/日期.jsonl` 落 1 条；`v:1`；带 `cid`；`t` 合理 |
| H4 | 写 200 字 | 接受，但返回 warning（建议 ≤150）；超过 300 字拒绝 |
| H5 | 同一秒同文再写 | `skipped=duplicate`，不重复落盘 |
| H6 | 含「心疼/舍不得」等 | 自动带 1–2 个预设标签；自造标签被过滤 |
| H7 | 群聊/公开会话调用 write | 拒绝（群聊不写） |
| H8 | `today` / `status` / `search` | 条数、开关、关键词/标签/日期/limit 命中正确；关着也能回看历史 |
| H9 | 让模型写一条后进入下一轮对话 | 常识层「今天的心路历程」出现该条，行首 `- `；没有就不出这一段 |
| H10 | 同一天写很多条 / 超预算 | 从最近往前截；保留计数行；4000 是软上限，真到再议 4500 |
| H11 | 重启 DSH | 条目还在；常识层仍按当天加载；旧平铺文件按 `v:1` 读；坏行跳过 |
| H12 | 日记内容查记忆检索/链网 | 查不到（日记不进记忆检索/链网） |

## 五、自动唤醒 E2E

| # | 步骤 | 期望 |
| --- | --- | --- |
| W1 | `/wake` 打开，绑定测试会话，启用 | 默认 6 次/天、45 分钟、安静 23–08；`nextWakeAt` 有值 |
| W2 | 模拟 23:00 | 陪伴唤醒拒绝（quiet）；普通提醒放行 |
| W3 | 模拟 08:00 | 允许；不在安静时段 |
| W4 | 连续触发两次（间隔 <45 分钟） | 第二次 `min-gap` 拒绝 |
| W5 | 当天触发到上限 | `daily-cap` 拒绝 |
| W6 | 用户 20 分钟前说过话 | `user-active` 跳过（activeWindow>0 时） |
| W7 | 到点投递 | 只投到 **绑定的目标会话**；工作会话/最近活跃会话收不到 |
| W8 | 看投递内容 | `[WAKE]` 简报；1–2 句；最多 1 问；不提“定时/系统提醒”；不调用工具 |
| W9 | 查 raw/草稿 | 唤醒简报**没有**被当成用户原话写入；AI 的回复按正常旁听记录 |
| W10 | 连续 3 次不回应 | 第 2 次给关闭提示；第 3 次最后一句；第 4 次暂停 3 天 |
| W11 | 用户回一句 | 暂停解除，`ignoredStreak=0`，之后可正常唤醒 |
| W12 | 重启 DSH | 排程/目标会话/暂停状态保留；不会把上一轮重复投 |
| W13 | 看唤醒日志 | 有 schedule id；不写 prompt 正文；不写关心正文 |
| W14 | 提醒（reminder） | 保留原文；不套陪伴的 1–2 句限制；不受安静时段拦 |
| W15 | 目标会话不在/不可用 | 跳过并记日志，不投到别的会话 |

## 六、和音乐陪听的隔离检查

音乐陪听现在也走“绑定会话 + followup”。两条线共用同一个原则：

- 只投用户**明确绑定**的会话；没绑定不投。
- 不用“最近活跃”猜目标。
- 系统投递的消息带 source 标记，不进用户 raw。

验收时顺便确认：在音乐会话里触发日记/唤醒，不会串到工作会话；反之亦然。
